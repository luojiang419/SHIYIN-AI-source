## 当前状态

本报告针对“无限画布中的图片、视频节点在使用过程中突然集体变空，刷新页面或退出画布后重新进入又恢复”的现象进行源码、历史修复、测试覆盖、安装态数据和进程资源快照分析。

结论不是单一资源 URL 丢失，也不是画布数据被删除。当前问题由三类机制叠加：

1. Chromium/WebView2 在大规模媒体子树、世界坐标 `transform` 与 `content-visibility` 组合下存在绘制/合成失效风险。
2. 当前媒体队列只限制“同时开始多少次加载”，没有限制“最终保留多少已解码媒体”，画布访问范围越大，解码内存与 GPU 栅格压力越高。
3. 媒体队列自身还存在完成计数、超时、取消和全场扫描缺口，会造成并发上限失真、队列槽位饿死及平移帧成本随节点总量增长。

因此，该现象应定级为 **P0 稳定性问题**。继续增加局部 CSS 例外或重新调度队列只能缓解某一种触发条件，不能形成长期稳定方案。

## 下一步

若进入修复开发，首先执行：

1. 为媒体队列补充可复现故障测试：预览失败后原图回退、永久挂起请求、节点脱离 DOM、连续平移 10 分钟。
2. 修复 `settle once`、超时、取消、代际令牌和真实优先队列，先消除队列失真与饿死。
3. 引入“可视区 + overscan + selected/running 保留”的媒体激活窗口，并对远区媒体执行延迟卸载。
4. 用 438 节点真实结构的脱敏副本执行 WebView2 像素、内存、GPU 和交互回归。
5. 再进入空间索引和节点 DOM 虚拟化，逐步移除对 `content-visibility:auto` 的核心依赖。

## 一、现象定性

### 1. 用户看到的“空”可能来自两条不同故障链

**A. 已经加载过的图片/视频同时消失，但节点边框、端口或文字仍在。**

这更符合浏览器绘制/合成层失效或 GPU 资源压力。媒体数据仍在 DOM 中，`img.src` 也可能仍然有效，只是媒体子树没有被正常栅格化。刷新后重新创建文档、DOM 和合成层，因此恢复。

**B. 新移动到视口内的节点一直没有图片，DOM 中只有 `data-preview-src`，没有有效 `src`。**

这更符合媒体队列停止排空、槽位被挂起请求占满或增量 DOM 生命周期缺口。刷新后 JS 队列计数归零并重新全量调度，因此恢复。

当前用户描述可能同时包含 A、B 两类空白。修复时必须分别观测，不能继续统一归因于“图片加载慢”。

### 2. 不支持“画布数据丢失”为主因

- 刷新或重新进入后同一节点再次出现，说明持久化的节点 URL 和节点模型仍然存在。
- 当前数据库中的最大活跃画布仍有 438 个节点且 revision 持续增长。
- 安装态日志中大量 `/api/media-preview` 返回成功，说明后端能够解析并返回多数本地媒体。

如果数据真的被覆盖为空，重新进入不会自动恢复原资源。因此，保存和数据库不是本现象的第一根因，但仍应保留 revision 冲突防护。

## 二、已确认的代码缺陷

### P0-1：媒体只有加载上限，没有驻留上限

经典画布在 `static/js/canvas.js:64-141` 将并发限制为 6，智能画布在 `static/js/smart-canvas.js:873-1035` 将并发限制为 5。队列向进入视口或安全边界的 `<img>` 写入 `src`，但媒体离开远区后不会移除 `src`、释放解码资源或降级到更小占位图。

结果是：

- 用户浏览过的媒体会持续驻留；并发为 6 不代表内存中只有 6 张图片。
- 438 个节点可以包含多张输出、参考图和视频首帧，真实媒体元素数量会明显大于节点数。
- 当前节点主预览普遍请求 768 宽缩略图；768×768 RGBA 的最坏解码占用约 2.25 MiB/张，数百张即可达到数百 MiB，且还未计算 DOM、合成 tile、原图预载和视频资源。
- Service Worker 的 512 MiB 是磁盘/CacheStorage 响应预算，不能约束浏览器的解码内存和 GPU 纹理。

这是现有方案最核心的架构缺口。

### P0-2：平移“修复”会暂时让全部媒体子树参与绘制

经典画布在 `static/css/canvas.css:274-280`、智能画布在 `static/css/smart-canvas.css:44-52` 使用 `content-visibility:auto` 跳过远区视觉子树。历史修复为了绕开 Chromium 在 transform 平移期间的误判，又在平移状态下强制所有相关子树：

```css
content-visibility: visible !important;
contain: none !important;
```

这能避免一类“平移时被错误跳过”的空白，但代价是平移期间大画布的全部媒体子树重新进入绘制评估。节点越多，主线程样式/布局、栅格和 GPU 内存峰值越高。

换言之，当前策略在两个风险之间切换：

- 静止时依赖 `content-visibility:auto`，承担 Chromium transformed subtree 绘制异常风险。
- 平移时禁用 containment，承担全量媒体绘制和 GPU 峰值风险。

这不是稳定的 LOD，而是浏览器启发式优化与全量绘制之间的动态切换。

### P0-3：预览失败回退可能使活动计数结算两次

经典 `startClassicPreviewImage()` 和智能 `startSmartPreviewImage()` 同时注册一次性 `load`、`error` 监听；预览 fallback 又单独注册 `error` 监听，并在预览失败时把同一个 `<img>` 的 `src` 改成原图。

可能出现以下顺序：

1. 预览请求触发 `error`，队列执行 `finish(false)`，活动计数减 1。
2. fallback 把 `src` 改为原图。
3. 原图成功触发此前尚未消费的 `load` 监听，再执行 `finish(true)`，活动计数再次减 1。

虽然代码用 `Math.max(0, active - 1)` 防止负数，但无法防止计数提前归零。后续队列会误以为还有空槽并继续启动请求，真实并发可能突破 5/6 的设计上限，进一步放大 I/O、解码和内存压力。

完成逻辑必须是幂等的 `settle once`，并在完成时解绑另一种事件监听。

### P0-4：队列没有超时、请求代际和真实取消

当前活动槽位只在 `<img>` 触发 `load` 或 `error` 时释放。若 Service Worker、远程代理、浏览器解码或连接处于长期 pending，槽位会一直占用。

- 经典画布的 `classicMediaQueuePending` 从未加入任务；所谓 `cancelClassicOffscreenPreviewTasks()` 实际没有可取消对象，并且没有调用点。
- 智能画布没有对应的 pending/cancel 任务模型。
- `<img src>` 注入没有任务 ID、代际令牌、超时 watchdog 或 AbortController。
- 节点被替换/移除后，请求仍会继续，直到浏览器自行结束。

当 5/6 个请求同时挂起时，新的可视节点将永久停留在 queued，退出页面后 JS 状态重置才恢复。

### P1-1：每次平移仍按全画布扫描 DOM

经典 `applyViewport()` 在 `static/js/canvas.js:2047-2052` 每帧安排 LOD 和媒体队列：

- `updateClassicSafeLod()` 在全量路径查询并遍历全部 `.node.canvas-lod-safe`。
- `drainClassicPreviewQueue()` 查询全部 `img[data-preview-src]`，对全部候选计算视口关系并排序。

智能画布在 `static/js/smart-canvas.js:3370-3421` 和 `1022-1031` 使用相同模式。

虽然 requestAnimationFrame 会合并同一帧重复调用，但复杂度仍是每帧 O(N) 节点扫描加 O(M log M) 媒体排序。现有矩形 Map 是按 ID 查询索引，不是空间索引，无法直接得到视口附近节点。

这会造成节点总量越大，平移每一帧越慢；即便画面中只看到十几个节点，也要检查数百或数千个节点。

### P1-2：同一媒体的多尺寸预览造成缓存与解码碎片

当前调用包含 256、512、768、1536、2048 等宽度，后端缓存键又把 width 纳入 key。同一文件会生成和缓存多个不同预览，浏览器也可能分别解码。

当前日志文件累计 5643 次预览请求中，768 宽占 4545 次，说明主节点媒体主要使用相对偏大的统一尺寸，而不是按实际屏幕像素需求自适应。

### P1-3：当前测试证明“代码字符串存在”，没有证明“像素不会空”

本次执行的 11 项测试全部通过，但关键测试主要检查：

- CSS 中是否存在平移保护规则。
- JS 中是否调用媒体队列调度函数。
- 队列并发常量和 data 属性是否存在。

它们没有覆盖：

- 真实 WebView2 的 `content-visibility + transform` 像素结果。
- 连续平移后的 renderer/GPU 内存曲线。
- 永久挂起请求导致的槽位饿死。
- 预览失败后原图成功导致的双重结算。
- 视口外媒体是否真正释放。

因此，“测试通过”与“用户现场不再空白”之间目前没有闭环。

## 三、为什么刷新或重新进入会恢复

刷新会同时重置四类状态：

1. 重建 DOM，重新触发图片解码与节点布局。
2. 重建 Chromium 合成层和 GPU tile，清除当前文档的异常绘制状态。
3. 将 `classicMediaQueueActive` / `smartMediaQueueActive` 归零，清除挂起或失真的前端队列计数。
4. 重新执行全量 render 和媒体队列调度，已有 Service Worker/磁盘预览缓存又能较快返回。

因此“刷新恢复”不是问题已经自愈，而是整个媒体运行时被销毁重建。这也是该问题会反复出现的直接原因。

## 四、推荐的更优架构

### 方案总原则

把当前“所有节点长期存在于 DOM，依赖 CSS 决定是否绘制”的方式，升级为：

**模型全量常驻，空间索引定位，DOM/媒体按视口窗口激活，连接层独立绘制，资源按预算回收。**

### 1. 媒体激活窗口

保留全部节点模型和几何信息，但只有以下媒体持有真实 `src`：

- 当前视口内节点。
- 视口四周 1～2 屏 overscan 节点。
- 被选中、正在生成、正在播放或正在编辑的节点。

远离视口的媒体在 2～5 秒 grace period 后：

- 暂停视频并清空 `src` / 调用 `load()` 释放解码器。
- 图片移除大缩略图 `src`，保留纯色、低清 64/128 占位或已知宽高。
- 节点模型中的 URL、尺寸、状态保持不变，重新进入窗口时从 CacheStorage/HTTP 缓存快速恢复。

资源预算应同时包含“最大激活媒体数”和“估算解码像素预算”，而不是只限制并发请求数。

### 2. 空间索引替代全场扫描

为节点矩形建立 RBush/R-tree 或分桶网格索引：

- 视口变化时直接查询相交节点 ID，复杂度接近 O(log N + K)。
- LOD、媒体激活、命中测试、小地图 dirty 更新共享同一空间查询结果。
- 只有进入/离开窗口的差集节点发生 DOM 或媒体变更。

对于当前固定 6000×4000 世界，也可以先使用简单均匀网格分桶，风险和实现成本低于直接引入复杂树结构。

### 3. 媒体任务状态机

每个请求使用独立任务对象：

```text
idle -> queued -> loading -> decoded -> active
                    |           |
                    v           v
                 failed       evicted
```

必须具备：

- `settled` 幂等保护，load/error/timeout 只能结算一次。
- generation token，旧 DOM/旧 URL 回调不能覆盖新节点状态。
- 10～15 秒 watchdog；视频/远程资源可以使用不同阈值。
- 离开激活窗口后取消未开始任务；可取消的 fetch 使用 AbortController。
- 图片与视频分队列；视频首帧并发低于图片。
- 失败采用有限次数指数退避，UI 保留占位和“重试”，不能显示纯空壳。

### 4. 节点 DOM 视口虚拟化

中期应让远区普通节点不再保留完整媒体 DOM：

- 数据模型、选择状态、端口几何和连接关系继续全量存在于内存索引。
- 视口窗口只挂载完整可交互 DOM。
- 远区节点由轻量 Canvas 层绘制边界/缩略占位，或仅保留极简 shell。
- 连接线和小地图使用 Canvas/SVG dirty-region 层，不依赖远区节点 DOM 的 `getBoundingClientRect()`。
- 节点进入视口时使用 DOM pool 复用，避免频繁创建大量控件和事件监听器。

完成该阶段后，`content-visibility:auto` 只能作为辅助优化，不能再承担正确性职责。

### 5. 统一缩略图规格和缓存语义

- 主节点默认使用 256/512 两档，根据实际 CSS 像素 × devicePixelRatio 选择；非必要不生成 768。
- 预览 URL 携带内容指纹（文件 mtime/size 或媒体对象 hash），响应使用长期 immutable cache。
- 内容指纹不变时采用 cache-first，不需要每 30 秒后台 revalidate。
- 内容变化时 URL 自然变化，不依赖旧 URL 的 SWR 刷新。
- 远程资源代理增加连接/读取超时、最大下载尺寸和可取消任务。

### 6. 自恢复与可观测性

运行时至少记录：

- 可视节点数、激活媒体数、queued/loading/decoded/evicted 数量。
- 最老 loading 任务耗时、超时数、失败回退数、重复 settle 次数。
- 当前解码像素估算、视频播放器数量、媒体 DOM 数量。
- 平移 frame interval p50/p95/p99、long task、LOD 差集规模。
- renderer/GPU 进程资源只能由桌面壳或诊断接口采集时，再加入本地诊断包。

当 `img.complete && naturalWidth > 0` 但可见节点仍疑似未绘制时，可对单个节点执行局部重新挂载/重设 `src`，不要让用户刷新整个画布。

## 五、建议实施顺序

### 阶段 A：队列正确性止血

- 修复双重结算。
- 增加超时、generation token、取消和挂起槽位恢复。
- 图片/视频分队列。
- 增加失败占位和局部重试。

风险低，能够直接消除“新视口节点一直 queued”的一类空白。

### 阶段 B：有界媒体驻留

- 增加激活窗口和延迟卸载。
- 统一 256/512 缩略图策略。
- 建立解码像素/媒体数预算。

这是解决长时间使用后集体空白和内存持续上涨的关键阶段。

### 阶段 C：空间索引与增量窗口

- 用网格/R-tree 查询视口节点。
- LOD 和媒体队列只处理窗口差集。
- 平移热路径不再 querySelectorAll 全场。

这是获得大画布稳定高帧率的关键阶段。

### 阶段 D：DOM 虚拟化与绘制层解耦

- 完整节点 DOM 只挂载可视窗口。
- 连接、小地图、远区占位独立绘制。
- 移除核心路径对 `content-visibility:auto` 的依赖。

这是长期架构升级，必须在 A/B/C 有测试保护后实施，不建议一次性重写整个画布。

## 六、验收标准建议

### 正确性

- 438 节点真实结构画布连续平移、缩放、框选和小地图拖动 10 分钟，任何时刻可视媒体不得集体空白。
- 注入 6 个永久挂起预览请求后，后续可视媒体能在超时回收槽位后继续加载。
- 预览失败、原图成功时活动计数只结算一次。
- 节点离开并重新进入激活窗口后，URL、选择、播放和生成状态保持正确。
- 刷新不再是恢复媒体显示的必要操作。

### 性能

- 500 节点画布平移 frame interval p95 不高于 20 ms，p99 不高于 33 ms。
- 2000 节点画布平移不出现超过 100 ms 的二次冻结。
- 媒体 DOM 数量由可视窗口决定，不随用户浏览过的节点总数单调增长。
- 重复遍历同一路径 5 次后 renderer/GPU 内存回到稳定区间，增长不超过首次稳定值的 15%。
- 缓存命中时可视媒体恢复 p95 不高于 300 ms；冷预览首批可视媒体 p95 不高于 1.5 秒。

### 测试体系

- Playwright/WebView2 截图执行像素非空检查，不只断言 DOM/CSS 字符串。
- 覆盖 50/200/438/500/1000/2000 节点，包含真实图片和视频首帧。
- 覆盖成功、404、415、断网、超时、慢响应、DOM 替换和快速往返视口。
- 每次发布前比较运行时脚本签名与源码签名，避免缓存旧代码干扰验收。

## 七、最终结论

当前无限画布已经做过增量渲染、媒体并发限制、缩略图缓存和 CSS LOD，方向并非完全错误；但现有实现只解决了“首次加载不要同时发太多请求”和“部分视口外节点少绘制”，没有建立完整的媒体资源生命周期。

严重 BUG 反复出现的根本原因是：

**画布规模是无界的，但 DOM、已解码媒体和 Chromium 合成压力仍接近全量常驻；现有 LOD 又依赖一个已经在现场暴露绘制异常的浏览器机制。**

更优秀的方案不是继续增加刷新、重绘或 CSS 强制规则，而是按顺序完成：

**队列状态机正确性 -> 有界媒体驻留 -> 空间索引 -> DOM 视口虚拟化 -> 像素与内存回归门槛。**

按此路径改造，可以在保持现有数据模型、节点功能和增量渲染成果的前提下，逐步提升稳定性，不需要立即推翻整个画布实现。

## 已知问题

- 当前没有抓取用户发生空白瞬间的 DevTools Layers、GPU trace 和 DOM 计算样式，因此“合成层失效”是高概率机制，不应写成已由 GPU trace 100% 证明。
- 当前内存数据是单点快照，后续必须增加时间序列和回落观测，才能区分合理缓存、持续增长和真正泄漏。
- 安装态日志未按单次画布会话聚合预览请求，5643 次只用于证明累计放大量级。
