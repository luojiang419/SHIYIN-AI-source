## 目标与约束

用户要求直接使用 `https://github.com/tigerowo/infinite-canvas` 的画布引擎，弃用现有卡顿引擎；保留页面布局和所有节点功能。修改运行源码前创建必要源码备份，以便恢复。默认不构建全量安装包。

## 当前证据

- 上游 `f30b8d7` 的 `infinite-canvas.tsx` 管理视口变换、平移、缩放和网格；编辑页 `canvas-client-page.tsx` 按视口筛选节点，节点通过 React 组件渲染，连线仍是 SVG。
- 本项目经典/智能画布是原生 DOM + SVG；业务事件、端口定位、媒体生命周期和节点模板直接依赖现有 DOM。只替换坐标变换无法获得上游的千节点性能。
- 旧性能审计中，每节点控件 DOM 膨胀和媒体请求洪峰是主要瓶颈；迁移验收需覆盖真实混合节点与媒体，不能只测空节点。
- 上游许可证 AGPL-3.0，本项目 `LICENSE` 包含商业使用限制；复制上游代码前需要确定分发许可是否兼容。

## 直接移植边界

上游没有独立的 npm 引擎包。可移植单元是 `infinite-canvas.tsx` 的视口容器、编辑页的可见节点筛选、`canvas-node.tsx` 的 React 节点挂载与 `canvas-connections.tsx` 的连线。只把容器嵌入当前页面，旧 `render()` 仍会全量重建 DOM，因此不符合用户要求。直接移植需把 React 渲染层作为唯一画布核心，停止经典/智能 `render()` 和 CSS transform 引擎直接操作画布根节点。

原有页面 shell、工具栏和浮层布局不迁移。现有工程数据仍是唯一持久化格式；React 层读取现有 `nodes`、`connections`、`viewport`，旧节点业务逻辑通过逐类型适配进入 React 节点组件。特殊节点的媒体、3D 舞台、提示词输入和端口必须在组件挂载/卸载生命周期中保留状态。布局 CSS 和 DOM 锚点通过截图及功能测试逐一核对。
