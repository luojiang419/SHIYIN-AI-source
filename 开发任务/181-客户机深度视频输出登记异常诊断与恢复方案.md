## 结论及边界

当前源码 canvas_core/video_depth.py 在 worker 退出码为0后读取 outputVideoPath，转换媒体 URL；`not output_path.is_file()` 或 `not output_url` 共用上述错误。节点仅在任务状态 done 时接收 outputUrl，因此服务将任务标为 failed 就不会显示结果。

已定位到“worker 成功退出之后、节点接收结果之前”的输出登记关口。日志没有区分文件不存在与URL映射失败；用户所说文件存在支持路径映射/返回路径异常的方向，但仍需核对是否就是该任务对应的文件。不能声称具体根因或 Codex 修改责任已经查明。

本地源码另有后台线程不显式传递账号上下文的风险；现场报告为 admin，默认线程上下文也是 admin，不能直接把这个通用风险当作本次根因。

## 实施方案

1. 保存现场证据：在客户机读取失败任务返回、对应 depth_video_<taskId> 目录及 run-metadata.json；记录 worker 返回路径、实际输出路径、媒体根目录和应用文件哈希。核对本机 Codex 修改与官方版本差异，保留修改副本和工程数据。
2. 定向修复输出登记：以任务创建时确定的账号与输出根目录为依据，校验结果位于该任务授权目录；规范化绝对路径与真实路径。分别报告文件缺失、文件无效、路径超界、URL映射失败。兼容旧结果字段时，仅回退到当前任务目录中已验证的 depth-preview.mp4，不能扫描任意目录并取最新视频。
3. 恢复已有成果：按任务ID和元数据匹配原节点与视频；先验证文件非空、视频可解码和媒体URL可访问，再恢复结果引用。操作前备份目标工程，不能把深度结果重新作为输入触发重复推理。任务记录应持久化，重启后可恢复状态。
4. 客户机版本收敛：现场核对后使用已发布2.0.0基准安装包覆盖升级并保留用户数据，再应用包含修复的正常热更新。升级本身不能替代输出登记修复，也不能保证自动找回旧节点。保留现有模型和CUDA 12.8运行时，无需重新发布模型或构建全量安装包。

## 验收标准

- 针对同一失败任务，现有视频恢复到原深度视频节点，可播放且保存、重开工程后仍存在。
- 新短视频任务最终返回 done 和有效 outputUrl；媒体访问及Range播放正常。
- 账号隔离、输出路径含中文/空格、目录映射、worker返回路径异常有针对性验证。
- 后端重启及短暂轮询断线不会永久丢失已完成结果。
- 现场验证后才宣告客户机恢复；当前仅完成日志诊断与方案设计。
