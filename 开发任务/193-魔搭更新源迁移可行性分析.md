## 结论

可以实现，而且客户端最终体验可以与 GitHub Releases 基本一致：自动检查版本、展示更新说明、下载、SHA-256 校验、断点续传、安装并重启。魔搭不提供 GitHub Releases 完全相同的 API，因此不能只替换域名；需要让客户端读取 SHIYIN 自己定义的更新清单，再从魔搭仓库下载版本化文件。

推荐架构：

1. 同局域网时继续使用现有独立分发中心，它已经具备签名清单、断点续传、完整检查点和增量热更新能力。
2. 不在局域网或局域网源不可达时，使用魔搭公开仓库作为公网源。
3. GitHub 暂时排在最后，仅用于让仍运行旧更新器的用户收到一次过渡版。
4. 过渡完成后，新版客户端不再需要代理访问 GitHub；GitHub 源可保留为人工灾备，但不参与日常自动更新。

这不会把“完整热更新基准检查点”变成全量安装包。项目现有发布定义保持不变：`2.0.0` 是全量安装基准包，`20260918084551` 是完整热更新基准检查点，其后的 `app/web` 包是纯前端热更新。

## 现状证据

`src-tauri/src/updater.rs` 的旧全量更新路径硬编码请求：

```text
https://api.github.com/repos/luojiang419/SHIYIN-AI/releases/latest
```

它解析 GitHub Release JSON，并要求同时存在：

```text
SHIYIN-AI-Setup-X.Y.Z.exe
SHIYIN-AI-Setup-X.Y.Z.exe.sha256
```

因此，旧客户端只能先从 GitHub 得到一个改变更新源的版本。服务端无法远程改变旧 EXE 中的硬编码 URL。

当前 2.0.x 热更新路径已经不同：`src-tauri/src/hot_updater.rs` 读取局域网分发中心 `/v1/catalog`，验证 Ed25519 签名、文件大小和 SHA-256，并下载 `.shiyin-update` 单包。`tools/build-hot-update.py --publish` 当前只导入本机独立分发中心。因此迁移公网源时应复用这套受信任清单语义，而不是继续模拟 GitHub Release JSON。

## 魔搭能力核验

建议创建独立公开模型仓库，例如：

```text
<namespace>/shiyingai-updates
```

公开仓库的匿名文件下载地址形式为：

```text
https://modelscope.cn/api/v1/models/<namespace>/shiyingai-updates/repo?Revision=master&FilePath=<encoded-path>
```

本机安装的 ModelScope SDK 1.36.3 已提供：

- `create_repo(..., visibility="public", repo_type="model")`
- `upload_file(...)` 和 `upload_folder(..., max_workers=8)`
- 大于 1 MiB 自动使用 LFS
- 分支/标签 revision 和 `create_model_tag(...)`
- 单文件客户端检查上限默认 100 GiB

下载端实测支持匿名访问和 Range。更新器可以继续使用现有的 `.part` 文件、重试、长度和 SHA-256 校验逻辑。

仍需通过真实仓库确认的项目包括：普通软件安装包是否符合魔搭仓库用途、单仓库存储、每日下行流量、请求频率、并发限制、CDN 缓存行为和超额后的处理方式。SDK 的 100 GiB 是客户端校验常量，不是平台额度承诺。

## 仓库布局与发布协议

建议使用不可变版本目录，并让唯一的可变入口最后发布：

```text
public/latest.json
public/latest.json.sig
releases/20260918084551/manifest.json
releases/20260918084551/manifest.json.sig
releases/20260918084551/SHIYIN-Hot-Update-20260918084551.shiyin-update
installers/2.0.0/SHIYIN-AI-Setup-2.0.0.exe
installers/2.0.0/SHIYIN-AI-Setup-2.0.0.exe.sha256
```

`latest.json` 至少记录协议版本、发布类型、版本、最低桌面宿主版本、更新说明、包路径、大小、SHA-256 和发布时间。客户端先验证 `latest.json.sig`，再下载包并核对大小与 SHA-256。签名沿用现有 Ed25519 公钥；私钥只留在发布机或分发中心数据目录，不能上传魔搭或 Git。

发布顺序必须是：

1. 构建版本化包和清单并在本地校验。
2. 上传不可变的版本目录。
3. 从匿名公网 URL 回读整包或抽样 Range，并核对长度与 SHA-256。
4. 最后上传 `public/latest.json` 和签名，使新版本对客户端可见。
5. 发布失败时不更新 `latest.json`；回滚内容时以新的更高发布序号重新发布，不能原地覆盖旧包。

由于 `master` 是可变引用，版本清单内的资产路径和哈希必须不可变。若魔搭标签 API 的下载稳定性通过实测，也可给每次发布创建标签并在清单中固定 revision；无论是否使用标签，都不能只依赖 `master` 当前内容来证明完整性。

## 过渡方案

旧 GitHub 用户需要一次过渡发布：

1. 先完成魔搭公网源支持，并把它编入符合项目基线约定的全量安装包。
2. 在 GitHub Releases 发布这一个过渡版，继续提供旧客户端能识别的 EXE 与 `.sha256` 文件。
3. 老客户端仍通过原 GitHub API发现并下载过渡版；安装后，新客户端按“局域网 → 魔搭 → 可选 GitHub 灾备”的顺序检查更新。
4. 魔搭同时发布对应的安装基准和热更新检查点，供新装、重装及后续增量更新使用。
5. 观察若干发布周期；只有确认活跃客户端已迁移后，才停止 GitHub 的日常 Release。长期离线且从未安装过渡版的旧客户端仍只能手动安装新基准包，因此 GitHub 过渡资产不应立即删除。

过渡版不应只改前端 JavaScript，因为 GitHub URL 位于 Rust 桌面宿主中。它必须包含新版桌面宿主；是否需要全量安装包取决于目标用户基线。按照当前项目约定，1.0.x 用户应通过 `2.0.0` 全量安装基准包覆盖升级，不能恢复已废弃的旧 bootstrap/updater 链。

## 实施范围

建议分四个独立阶段交付：

1. 仓库试验：创建公开测试仓库，上传 1 MiB、小型热更新和接近真实大小的完整热更新包；验证电信、联通、移动至少各一条网络，测试整包、Range 恢复、并发和连续下载。
2. 协议实现：增加与具体托管平台解耦的 `PublicUpdateSource`，解析并验证 SHIYIN 签名清单；局域网协议继续保持现状。
3. 发布工具：在 `tools/build-hot-update.py` 产物基础上增加显式的魔搭发布命令。token 只从环境变量或 ModelScope 登录缓存读取；上传后回读验证，最后原子切换 `latest.json`。
4. 迁移发布：先向魔搭发布，再制作和验证 GitHub 过渡版；记录下载成功率、错误类型和客户端版本分布。

建议不要让客户端依赖 ModelScope Python SDK。发布机可以使用 SDK，客户端只需普通 HTTPS GET，这样不会增加安装体积或 Python 依赖，并能保留现有 Rust 下载器的断点续传能力。

## 验收标准

- 国内无代理环境能匿名获取签名清单并完成更新。
- 首次下载中断后可从 `.part` 继续，服务端响应 Range，最终 SHA-256 一致。
- 篡改清单、签名、包体、大小或路径时客户端明确拒绝。
- 上传未完成或 `latest.json` 更新失败时，客户端仍看到上一版完整发布。
- 局域网源可用时保持优先；不可用时自动切换魔搭，不要求用户配置代理。
- 从 GitHub 旧版安装过渡版后，下一次检查不再访问 GitHub即可获取魔搭更新。
- 魔搭不可用时给出可理解的错误，并保留手动安装基准包的恢复入口。
- 发布日志记录版本、commit、文件大小、SHA-256、魔搭 commit/tag 和匿名回读结果，但不记录 token。

## 风险与边界

- 最大的不确定性是平台政策和实际下行配额，不是技术协议。正式承载用户更新前必须取得明确答案或用真实负载验证。
- 公共模型仓库中的文件可被任何人下载，因此包内不能包含密钥、用户数据或私有模型。代码保密依赖安装包本身并不成立。
- HTTPS 只能保护传输链路；更新信任必须由 Ed25519 签名和 SHA-256 完成。
- 魔搭域名或 API 形态未来可能变化。客户端应支持由已签名清单给出资产地址，发布工具集中封装 URL 生成，避免再次把平台细节散落在更新器中。
- 单一公网源仍有平台故障风险。现有局域网中心应保留；有条件时可再加自有对象存储/CDN作为第二公网镜像。
