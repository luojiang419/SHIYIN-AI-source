## 本轮最终结论

用户感知的“进入同一个画布要等很久”不是一个单点故障，而是版本演进后两类成本同时落在首屏关键路径上：

1. **直接 CPU 回归（P0）**：1.0.349（`3c0e607`）把原本只在选中节点显示的一套 `imageNodeQuickPromptHtml()` 浮层，改成每个图片节点都创建；1.0.340（`be737ff`）已经把图片/视频快捷工具栏常驻到每个节点。隐藏并不等于不付成本：每个节点仍要生成 textarea、select、button、图标和监听器，并参与样式计算。500 图片节点时 `#nodes.innerHTML` 约 4.92 MB，主线程出现约 4～11 秒长任务（不同机器/运行次数有波动）。
2. **直接 I/O 回归（P0）**：1.0.376（`f21c4c3`）把预览 `<img>` 从 `loading="lazy"` 改为 `loading="eager"`。当前后端虽已使用 4 线程池和 keyed Future，但它只能合并同一媒体的并发生成；435 个节点对应数百个不同媒体时，PIL/ffmpeg 仍按 4 个一批排队，且视口外请求可能先占满队列。
3. **缓存放大（P1）**：1.0.261 引入 Service Worker，1.0.273 将 API/无版本媒体改为 network-first；当前 1.0.376 对预览采用 stale-while-revalidate，但每次新的 `<img>` 请求仍无条件启动后台 refresh。Service Worker 版本更新时还会删除旧 generated-image cache，升级后的第一次进入天然是冷缓存。
4. **入口与资源竞争（P1）**：列表 iframe 内仍通过 `window.location.href` 整页切到 `canvas.html`；当前编辑器脚本/样式和扩展脚本约 1.8 MB，宿主又以 3 路并行预热其它 iframe，WebView 主线程、网络和内存互相竞争。
5. **数据/渲染放大（P1）**：打开时仍会全量构造节点、端口、事件、连线和小地图；重复 render 还会重新创建上述每节点 UI。历史 smart 多图节点在统一入口迁移时可能拆成多个 classic 子节点，节点和媒体数按倍数增长。
6. **尾延迟放大（P2）**：异步 `/touch` 会重新读取并序列化完整画布写入 SQLite；资源检查、任务恢复、文件维护和模型校验也会在启动后争用磁盘。它们通常不是 4～7 秒长任务的首因，却会拉长“全部可用”的时间。

因此，“174 秒开、175 后慢”的准确表述是：**在可追溯源码层面，175 本身没有改动画布渲染算法；174 没有独立提交，且 174 构建阶段已经带有缓存键门禁改动，175 又将这套盖章逻辑正式保留下来。它可能改变实际加载的资源版本并造成一次冷缓存。随后 340/348 的节点工具栏膨胀、349 的每节点提示词面板，以及 376 的 eager 媒体洪峰，才是当前长等待的主要可执行根因。**

## 174→175 结论（先回答版本疑问）

- `1.0.174` 没有独立源码提交；本地记录显示它基于 `7a4765f`（源码 `VERSION=1.0.173`）和未提交的安装缓存门禁改动构建。
- `1.0.175` 对应 `2f2a2f0`。`static/js/canvas.js`、`static/js/smart-canvas.js`、`static/canvas.html`、`static/js/canvas-list.js` 在两个提交中的 blob SHA 完全相同；差异仅在 Topaz、版本同步、安装脚本和依赖锁文件。
- 174 的任务快照已经记录“同时改写 `?v=` 与 `&v=`”的缓存门禁；175 对应提交把该构建脚本和门禁纳入正式 Git。它会让更多旧 URL 失效、触发一次冷加载，但不是每次节点 render 的算法回归。
- 175 前后两版都使用 lazy 预览；因此若用户是在“刚升级后第一次打开”观察到变慢，缓存冷启动是合理解释；若在后续版本持续变慢，应优先看 349/376 的变化。
- 还要区分一段历史首开问题：175 时 `window.onload` 先 `await loadConfig()`，配置完成后才 `openCanvas()`；1.0.179 又加入 MiniMax H3 状态探测，配置里存在 RunningHub 工作流或 H3 时会把外部网络探测放在画布之前。该串行链直到 1.0.228 的 `c67a39c` 才移到首屏后。它能解释 175–228 期间的“点击后一直等”，但不是 175 提交本身新增的画布算法。

两个关键反事实：

- HEAD 只把 eager 改回 lazy，预览请求降到 70，但首屏仍约 12.6 s，说明当前“等很久”的 CPU 主因是 DOM/CSS，而不是网络 alone。
- HEAD 去掉 prompt+toolbar 后，500 节点恢复到约 1.6–2.2 s；因此 1.0.349 是数量级回归点，1.0.376 是在其上叠加的 I/O 洪峰点。

节点类型会改变基线：额外的 500 generator 合成测试中，1.0.175 本身约 8.2 s、包含 2,500 个 select 和 2,500 个 button；1.0.176 的 inline prompt 只增加约 178 KB HTML、约 75 ms。也就是说，“500 个节点”不能替代“500 个什么节点、含多少媒体和控件”；本报告的主 A/B 以当前安装态占多数的 image/output 混合路径为重点。

同一 HEAD 场景的 Chrome tracing 进一步显示：完整 DOM 的 `Layout` 总耗时约 5,129.8 ms、`UpdateLayoutTree` 约 9,642.5 ms、`ParseHTML` 约 314.4 ms、`Paint` 仅约 13.2 ms；去掉每节点 prompt+toolbar 后分别降到约 333.9 ms、451.6 ms、40.6 ms、8.5 ms。这个数量级差异把主要责任定位到样式树/布局，而不是 JavaScript 下载、脚本解析或 Canvas 绘制。

完整 HEAD 合成 DOM 的计数约为：500 个 prompt panel、500 个 media toolbar、500 个 textarea、4,000 个 select、5,500 个 button 和约 5,500 个图标节点（每图片节点约 9.8 KB HTML）。这些控件虽然大多 `visibility:hidden`，仍会被样式匹配、布局和事件绑定处理。

历史串行链也做过延迟注入复测：在 1.0.175 页面把 `/api/runtime/config` mock 延迟 2 s，首个节点从约 1.10 s 变为约 3.06 s；再把 `/touch` 与资源检查各延迟 2 s，首个节点约 5.11 s。当前 HEAD 的配置并行、首屏后 touch/检查在同样延迟下首个节点仍约 1.48 s。由此可把 175–228 期间的网络/配置等待与 349 之后的 DOM 布局回归区分开。

此前统一性能 fixture 在 500 节点/1000 连线下记录的纯 render p95 约 68.7 ms、智能画布约 67.9 ms（`进度快照/630-统一验收fixture基线与交互观测.md`），也说明“全量节点本身”不是秒级等待的充分条件；每节点 UI 和媒体副作用才改变了量级。

## 当前安装态数据旁证（仅聚合统计）

本机 1.0.376 安装态数据库中，最大画布约 435 个节点、1,273 个媒体 URL 引用、521 个唯一地址、约 98 个唯一视频地址，含 120 条日志，payload 约 418 KB。安装态日志中同一画布的单次打开区段可见约 456～485 次 `/api/media-preview`（约 402～423 次为 768px，另有 256/512/1536px 变体）。这些日志含历史 QA 活动，作为旁证而非纯净用户 p95；但请求量与源码路径完全吻合。

当前同一批媒体按缓存宽度的命中并不均匀：768px 约 508/518 已有预览，256px 约 431/518，512px 约 24/518，1536px 约 20/518。由于缓存键包含宽度，同一文件在不同 UI 位置会生成多份缩略图；升级清理旧 SW cache 后这些命中还会全部归零。

后端真实文件微基准（临时目录输出、随后清理）显示：84 张共约 333.5 MB 的大图生成 768px WebP，4 线程 wall time 约 2.44 s，单文件耗时 median 约 58 ms、p95 约 440 ms、最大约 600 ms；按文件尺寸和机器不同，500 个独立媒体的排队尾延迟达到十几秒是合理的量级。该估算不代表每台机器的固定 p95，但说明 keyed Future 不能替代对独立媒体数量和优先级的控制。

## 证据链

### 1. 点击工程会触发编辑器整页冷启动

- `static/js/canvas-list.js:498-503` 的 `openCanvas(c)` 使用 `window.location.href = /static/canvas.html?...`。
- 该调用发生在画布列表 iframe 内，因此不会复用列表页的 JavaScript 运行时，也不会只替换画布数据。
- `static/canvas.html:23-39,515-523` 同时加载大量 CSS、vendor 和功能脚本；当前文件大小统计如下（未压缩，未计入 vendor 与字体）：

| 资源 | 大小 |
| --- | ---: |
| `static/js/canvas.js` | 1,158,844 B |
| `static/js/canvas-special-nodes.js` | 110,116 B |
| `static/js/canvas-film-nodes.js` | 43,252 B |
| 其他画布业务脚本 | 约 137 KB |
| `static/css/canvas.css` | 200,405 B |
| `static/css/studio-unified.css` | 114,625 B |
| 业务脚本与样式合计 | 约 1.79 MB |

- 这些脚本位于 body 末尾但没有 `defer`/模块拆分；浏览器仍需下载、解析、编译后才触发 `window.onload`。
- 经典画布 `window.onload`（`static/js/canvas.js:22416-22441`）在拿到 URL 参数后才开始 `openCanvas(openId)`；智能画布同样在 `static/js/smart-canvas.js:21310-21330` 等待 `loadCanvas()`。

### 2. iframe 预热会与点击进入竞争

- 宿主页 `static/index.html:2647-2651` 配置了 3 路并行 iframe 预热。
- `static/index.html:2702-2733` 为除当前页面外的页面设置 `src`，每个 worker 等待最多 1.8 秒；其中 canvas iframe 预热的是 `canvas-list.html`，不是实际的 `canvas.html`。
- 用户点击画布工程时，canvas iframe 需要从列表页再次导航到编辑器页，而其他 iframe 可能仍在下载、解析和执行 `ecommerce.js`、`asset-manager.js`、`works.js` 等脚本。该阶段会争用 WebView 主线程、网络连接和内存。
- `9a71d89 perf: 缓存静态资源并并行预热页面` 将原先的顺序预热改为 3 路并行；这解释了为什么“预热全部页面”在理论上减少导航等待，但在用户抢先进入画布时可能制造瞬时峰值。

### 3. 画布打开后仍是全量 DOM 构造

经典画布：

- `static/js/canvas.js:3290-3327` 获取整个画布 JSON 后立即执行 `nodes = canvas.nodes`、`connections = canvas.connections` 和 `render()`。
- `static/js/canvas.js:8286-8346` 的 `render()` 遍历全部节点，调用 `renderNode(node)`，重新 append 全部节点，随后执行几何刷新、图标刷新、媒体 fallback 绑定、图片尺寸测量和 minimap 调度。
- `static/js/canvas.js:10033-10380` 的 `renderNode` 会为图片/视频节点创建预览元素、绑定多个事件；组节点还会通过 `nodes.find` 解析成员。节点和连接较多时，CPU 开销随节点数、连接数和组成员数增长。

智能画布：

- `static/js/smart-canvas.js:7406-7471` 打开后会遍历节点做迁移、日志裁剪、运行态清理、输入清理、设置归一化，再调用 `render()`。
- `static/js/smart-canvas.js:9957-10073` 首次 render 会把全部节点 HTML 拼接进 template、解析成 DOM、重建连接、绑定节点/连接事件、更新 Composer 和 minimap。
- 历史版本的智能画布部分调用没有统一 lazy；当前版本经 `f21c4c3` 后，经典/智能缩略图统一为 `loading="eager"`，因此不能再用旧版“部分 lazy”描述当前行为。

### 4. 本地媒体预览逐张生成，存在严重并发放大

前端：

- `static/js/canvas.js:49-62` 与 `static/js/smart-canvas.js:810-823` 将 `/output/`、`/assets/` 图片和视频转换成 `/api/media-preview?w=...&url=...`。
- 当前 `render()` 会一次创建所有预览 `<img>`；`loading="eager"` 使所有节点（包括视口外节点）立即进入浏览器请求队列。不同显示位置还会请求 256/512/768/1536 等多个宽度。
- 历史版本的尺寸测量会为所有图片创建原图请求；当前已改为主要在选中节点/空闲阶段测量，但不同组件仍可能请求多种预览宽度。

后端：

- `main.py:7176-7291` 每个 `/api/media-preview` 请求都会执行路径解析和 stat；缓存不存在时调用 PIL，视频则启动 ffmpeg 抽帧。
- 当前代码已经有 `ThreadPoolExecutor(max_workers=4)` 和 keyed in-flight Future（`main.py:7190-7271`），能合并同一文件/尺寸的同时生成；但对数百个不同媒体没有视口优先级、队列上限或负缓存，仍会按 4 个一批排队。
- 旧版 `49b21e8` 的 network-first 和当前 SWR 都会在新的 `<img>` 请求上触发网络路径；当前 SWR 即使命中缓存也会后台 refresh，重复 render 会放大请求数。
- 当前安装态最大画布已聚合到约 435 节点、521 个唯一媒体地址（约 98 个视频），足以稳定触发该路径；仓库样例数据库较小，不能代替安装态数据。

### 5. Service Worker 未解决首轮预览，且缓存命中有额外元数据开销

- `static/media-cache-sw.js:28-53` 只缓存特定媒体路径和预览 API。
- `static/media-cache-sw.js:60-68` 的 `needsFreshNetwork` 对没有版本参数的 URL 返回 true；普通 `/output/`/`/assets/` URL 通常没有内容版本，因此首次和刷新优先走网络。`/api/media-preview` 当前走单独的 SWR 分支，但每次新请求仍启动后台刷新。
- `static/media-cache-sw.js:109-143` 的缓存写入会执行 `readMeta()`、`writeMeta()` 和 `trimCache()`；非预览图片命中路径还会读取整组 IndexedDB 元数据。大量缩略图并发时，这些事务会与媒体请求竞争。
- 当一个画布同时加载大量缩略图时，这些 IndexedDB 操作会与图片请求并发发生。它们不是主要根因，但会放大首屏 I/O 和 WebView 调度压力。

### 6. 打开后的后台请求和启动任务仍会争用

经典画布在首次 render 后立即启动：

- `static/js/canvas.js:3314-3317` 恢复图片/视频/Topaz 任务并启动远程轮询。
- `static/js/canvas.js:3320-3327` 异步调用 `/touch` 和 `/api/canvas-assets/check`。
- `/touch` 后端 `main.py:20119-20126` 会重新加载完整画布并调用 `save_canvas`；对于大画布，这会再次 JSON 序列化并写入 SQLite。
- 资源检查 `main.py:20134-20145` 最多接收 3000 个 URL；虽然检查本身是轻量的，但请求体可能很大。

启动后台任务：

- `main.py:485-536` 的维护任务在启动 2.5 秒后开始，包含资产迁移、文件扩展名迁移、本地上传索引和视频片段对账。
- `main.py:538-557` 的任务恢复在 4 秒后开始，读取持久化任务并恢复状态。
- 两者都通过 `asyncio.to_thread` 执行，但仍会争用默认线程池和 SQLite；“不阻塞 `/api/health`”不等于“不影响用户点击后的请求”。

## 根因分级（按当前源码和复测排序）

### P0-1：1.0.340～1.0.349 每媒体节点 UI 造成 CSS/布局长任务

`be737ff`（1.0.340）先把媒体工具栏常驻到每个图片/视频节点，`d5e97d9`（1.0.348）又扩大了操作项；`3c0e607`（1.0.349）再将 `imageNodeQuickPromptHtml()` 从“单个选中浮层”搬进每个图片节点。500 个图片节点因此会额外生成数千个表单控件、图标和事件监听器；每次 render 还会为每个节点重复读取/解析工具栏偏好、生成 provider/model options。受控 trace 显示 `UpdateLayoutTree + Layout` 合计约 14.8 秒，而 `ParseHTML` 仅约 0.31 秒、`Paint` 约 0.013 秒，说明主要不是脚本下载或 GPU 绘制，而是 DOM 样式树和布局计算。

这里还有一个容易被忽略的结构性原因：现有 LOD 的 `content-visibility:auto` 只包住 `.node-visual-shell`，而 prompt panel 和 media toolbar 被追加在 `.node` 外层（`renderNode` 中先 append 两个浮层，再 append visual shell）。所以即使节点本体被 LOD 跳过，500 个节点的浮层仍全部参加样式匹配和布局；这也是之前的 LOD 优化没有抵消 349 回归的原因。与此同时，`renderNode` 还会对每个节点内所有 `button/select/textarea/input` 各绑定多个监听器，重复 render 时这些闭包和 DOM 控件一起被重建，进一步增加 GC 和主线程压力。

### P0-2：1.0.376 eager 预览把媒体 I/O 推入首屏

`f21c4c3` 将预览从 lazy 改为 eager。当前后端虽已使用 4 线程池和 keyed Future，但它只能合并同一媒体的并发生成；435 个节点对应数百个不同媒体时，PIL/ffmpeg 仍按 4 个一批排队，且视口外请求可能先占满队列。

### P1：Service Worker 的版本失效、network-first/SWR refresh 放大请求

1.0.261 引入 SW，1.0.273 将 API/无版本媒体改为 network-first；当前预览改为 SWR 后，命中缓存可以先显示，但每个新 `<img>` 仍启动 refresh，且版本切换会删除旧 generated-image cache。宽度不同也产生不同缓存键。

### P1：整页导航、编辑器资源膨胀和 iframe 预热竞争

画布列表仍在 iframe 内用 `window.location.href` 切换到编辑器；当前 canvas 业务脚本从 175 时约 775 KB 增至约 1.16 MB，并加载 16 个脚本/多份 CSS。宿主的三路预热会在用户抢先点击时共享 WebView 主线程和连接池。

### P1：全量 render、重复 render 和历史 smart 迁移

打开、资源检查回调、配置回调及部分任务恢复都会触发完整 render；每次都会重建节点 UI、连线、几何和小地图。统一入口对历史 smart 多图节点的迁移可能把一个节点拆成多个 classic 子节点，使后续 DOM/媒体数量按倍数增长。

### P2：完整 payload touch/save 与启动后台任务争用

SQLite 以整段 `payload_json` 保存画布；`/touch` 会再次读取、JSON 序列化并写回。启动后的维护、任务恢复、模型校验和资源检查会增加尾延迟，但从受控 trace 看不是当前 4～7 秒布局长任务的首因。

## 建议的整改顺序

### 第一阶段：先止血（不改变画布数据模型）

1. 把图片快捷提示词面板恢复为一个共享的选中浮层；媒体工具栏只在 hover/selected 时动态挂载，或采用事件委托，禁止每个节点常驻表单。
2. 预览采用“视口优先 + 有界队列”：先发起可视区及安全边界请求，非视口任务延后；图片和视频分开限流，视频低并发。
3. 保留 keyed Future，但增加失败负缓存、耗时/队列日志，并让同一文件不同组件尽量复用统一缩略图尺寸。
4. Service Worker 将内容寻址的媒体缓存与静态资源版本解耦；升级时不删除仍由文件 mtime/size 校验的预览；SWR refresh 需要去重和节流。
5. 预热期间用户点击画布时暂停其它 iframe 预热，或暂时把并发降为 1。

### 第二阶段：消除进入冷启动

1. 不在画布列表 iframe 内用 `window.location.href` 打开编辑器；改为在同一个画布宿主中维护 list/editor 两个视图，或预热一个真正的 `canvas.html` 文档并通过消息传入 canvas id。
2. 将 canvas.js 拆分为首屏核心、特殊节点、生成 provider、设置面板等 chunk；首屏只加载节点渲染和交互必需代码，其余在 idle 阶段加载。
3. 保留当前的“先 render、后台 touch/资源检查”原则，但把真正编辑器文档纳入预热验收。

### 第三阶段：降低大画布 render 成本

1. 以节点索引和视口 bounds 做首屏虚拟化，只创建可视区及安全边界内的节点 DOM。
2. 连接、minimap、图标刷新按 dirty 集合更新；避免首次 render 后再次全量 refresh。
3. 将原图尺寸测量改为按选中节点或用户打开编辑器时执行，禁止首屏对所有图片创建 `new Image()`。
4. 对历史日志、输出数组和节点媒体做服务端/客户端分页或上限裁剪，并在保存前剔除不可持久化的大型 data URL。

### 第四阶段：建立可观测性和回归门槛

记录以下阶段耗时并上报本地诊断日志：

- `canvas_navigation_start → canvas_html_loaded`
- `canvas_html_loaded → api_canvas_response`
- `api_canvas_response → first_render_end`
- `first_render_end → first_preview_paint`
- `/api/media-preview` 排队、生成、命中、失败耗时
- 首屏媒体数量、可视媒体数量、节点数、连接数、画布 JSON 字节数
- 长任务数量和最大持续时间

建议验收门槛：

- 轻量画布（≤50 节点、≤20 媒体）：首次进入到可交互 ≤1.5 秒。
- 中型画布（≤200 节点、≤100 媒体）：首次进入到可交互 ≤3 秒；首屏可视媒体先于非视口媒体显示。
- 同一画布第二次进入：不重新生成已存在的预览，媒体命中率 ≥95%。
- 100 个媒体并发请求时，预览生成队列不会超过设定并发，服务端无重复生成。
- 启动后台维护/任务恢复期间进入画布，p95 不得超过空闲状态的 1.25 倍。
