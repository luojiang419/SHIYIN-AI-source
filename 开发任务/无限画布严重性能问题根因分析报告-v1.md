# 无限画布严重性能问题根因分析报告

状态：分析完成，待实施修复  
当前阶段：1/1  
最后更新：2026-08-30

## 当前结论

用户反馈的两个现象由同一条加载链上的多个瓶颈叠加造成：

1. **点击画布工程后进入慢**：`canvas-list.html` 在 iframe 内通过 `window.location.href` 整页切换到 `canvas.html`，导致编辑器 HTML、约 1.79 MB 的业务脚本与样式、vendor 资源重新下载/解析/编译；同时宿主页正在以 3 路并行预热其他 iframe，主线程和网络连接存在竞争。
2. **进入画布后资源长时间加载**：打开画布后虽然先执行 `render()`，但 render 会为所有节点重建 DOM；每个本地媒体缩略图都访问 `/api/media-preview`，服务端首次逐张调用 PIL 或 ffmpeg 生成预览，没有请求合并、并发上限或跨进程锁。媒体数量一多，CPU、磁盘和线程池会同时被打满。
3. **缓存策略没有覆盖首次慢路径，部分情况下反而增加开销**：Service Worker 对无版本媒体采用 network-first；每次缓存未命中都会写缓存并执行 IndexedDB 元数据读写/清理。媒体预览 URL 没有内容版本号，因此首轮仍然走网络和缩略图生成。
4. **后台任务会在启动后 2.5～4 秒与用户请求争用资源**：延迟维护和任务恢复虽已移出健康检查，但它们仍使用线程池、SQLite 和文件遍历；用户在这个时间窗口点击画布时，仍可能感到明显停顿。

这不是单一“网络慢”或单一“数据库慢”。优先级最高的是限制/去重媒体预览、避免编辑器整页冷启动，以及暂停或降低 iframe 预热对画布进入的竞争。

## 证据链

### 1. 点击工程会触发编辑器整页冷启动

- `static/js/canvas-list.js:498-503` 的 `openCanvas(c)` 使用 `window.location.href = /static/canvas.html?...`。
- 该调用发生在画布列表 iframe 内，因此不会复用列表页的 JavaScript 运行时，也不会只替换画布数据。
- `static/canvas.html:23-39,515-523` 同时加载大量 CSS、vendor 和功能脚本；当前文件大小统计如下（未压缩，未计入 vendor 与字体）：

| 资源 | 大小 |
| --- | ---: |
| `static/js/canvas.js` | 1,158,844 B |
| `static/js/canvas-special-nodes.js` | 110,116 B |
| `static/js/canvas-film-nodes.js` | 43,252 B |
| 其他画布业务脚本 | 约 137 KB |
| `static/css/canvas.css` | 200,405 B |
| `static/css/studio-unified.css` | 114,625 B |
| 业务脚本与样式合计 | 约 1.79 MB |

- 这些脚本位于 body 末尾但没有 `defer`/模块拆分；浏览器仍需下载、解析、编译后才触发 `window.onload`。
- 经典画布 `window.onload`（`static/js/canvas.js:22416-22441`）在拿到 URL 参数后才开始 `openCanvas(openId)`；智能画布同样在 `static/js/smart-canvas.js:21310-21330` 等待 `loadCanvas()`。

### 2. iframe 预热会与点击进入竞争

- 宿主页 `static/index.html:2647-2651` 配置了 3 路并行 iframe 预热。
- `static/index.html:2702-2733` 为除当前页面外的页面设置 `src`，每个 worker 等待最多 1.8 秒；其中 canvas iframe 预热的是 `canvas-list.html`，不是实际的 `canvas.html`。
- 用户点击画布工程时，canvas iframe 需要从列表页再次导航到编辑器页，而其他 iframe 可能仍在下载、解析和执行 `ecommerce.js`、`asset-manager.js`、`works.js` 等脚本。该阶段会争用 WebView 主线程、网络连接和内存。
- `9a71d89 perf: 缓存静态资源并并行预热页面` 将原先的顺序预热改为 3 路并行；这解释了为什么“预热全部页面”在理论上减少导航等待，但在用户抢先进入画布时可能制造瞬时峰值。

### 3. 画布打开后仍是全量 DOM 构造

经典画布：

- `static/js/canvas.js:3290-3327` 获取整个画布 JSON 后立即执行 `nodes = canvas.nodes`、`connections = canvas.connections` 和 `render()`。
- `static/js/canvas.js:8286-8346` 的 `render()` 遍历全部节点，调用 `renderNode(node)`，重新 append 全部节点，随后执行几何刷新、图标刷新、媒体 fallback 绑定、图片尺寸测量和 minimap 调度。
- `static/js/canvas.js:10033-10380` 的 `renderNode` 会为图片/视频节点创建预览元素、绑定多个事件；组节点还会通过 `nodes.find` 解析成员。节点和连接较多时，CPU 开销随节点数、连接数和组成员数增长。

智能画布：

- `static/js/smart-canvas.js:7406-7471` 打开后会遍历节点做迁移、日志裁剪、运行态清理、输入清理、设置归一化，再调用 `render()`。
- `static/js/smart-canvas.js:9957-10073` 首次 render 会把全部节点 HTML 拼接进 template、解析成 DOM、重建连接、绑定节点/连接事件、更新 Composer 和 minimap。
- 智能画布的图片缩略图 HTML（`static/js/smart-canvas.js:820-823`）默认没有经典画布那样的 `loading="lazy"`/`decoding="async"`；只有部分调用方额外传入 lazy 属性。因此智能画布的资源并发更不可控。

### 4. 本地媒体预览逐张生成，存在严重并发放大

前端：

- `static/js/canvas.js:49-62` 与 `static/js/smart-canvas.js:810-823` 将 `/output/`、`/assets/` 图片和视频转换成 `/api/media-preview?w=...&url=...`。
- 画布 render 会一次创建所有预览 `<img>`；即使使用了 lazy，浏览器仍可能把变换后的世界坐标中大量节点判定为接近可视区，且智能画布部分调用没有 lazy。
- `static/js/canvas.js:8253-8283` 和 `static/js/smart-canvas.js:825-833` 还会为原图读取尺寸，形成额外的原图请求。

后端：

- `main.py:7222-7257` 每个 `/api/media-preview` 请求都执行 `output_file_from_url`、文件 stat，并在缓存不存在时在线程中调用 PIL；视频则启动 ffmpeg 抽帧。
- 缓存键包含文件 mtime、大小和宽度，但没有进程内 in-flight 去重。同一文件在并发请求到达时可能重复进入 `_build_preview()`。
- `asyncio.to_thread(_build_preview)` 没有专门的并发信号量。几十张图片/视频同时首次打开时，会同时占用默认线程池、PIL 解码、ffmpeg 子进程和磁盘写入。
- 当前工作区统计到 `generated-images` 目录约 437 个文件、约 1.5 GB；这不是某个具体用户画布的精确数量，但说明本地媒体规模足以触发该路径的放大效应。仓库样例数据库中的画布很小，不能代表真实用户数据。

### 5. Service Worker 未解决首轮预览，且缓存命中有额外元数据开销

- `static/media-cache-sw.js:28-53` 只缓存特定媒体路径和预览 API。
- `static/media-cache-sw.js:72-78` 的 `needsFreshNetwork` 对没有版本参数的 URL 返回 true；`/api/media-preview` 以及普通 `/output/`/`/assets/` URL 通常没有内容版本，因此首次和刷新优先走网络。
- `static/media-cache-sw.js:117-143` 每次图片缓存命中都会 `readMeta()` 读取整个 IndexedDB 元数据集合，再 `writeMeta()` 更新 touched 时间；未命中写入后还会执行 `trimCache()`，再次读取、排序和删除元数据。
- 当一个画布同时加载大量缩略图时，这些 IndexedDB 操作会与图片请求并发发生。它们不是主要根因，但会放大首屏 I/O 和 WebView 调度压力。

### 6. 打开后的后台请求和启动任务仍会争用

经典画布在首次 render 后立即启动：

- `static/js/canvas.js:3314-3317` 恢复图片/视频/Topaz 任务并启动远程轮询。
- `static/js/canvas.js:3320-3327` 异步调用 `/touch` 和 `/api/canvas-assets/check`。
- `/touch` 后端 `main.py:20119-20126` 会重新加载完整画布并调用 `save_canvas`；对于大画布，这会再次 JSON 序列化并写入 SQLite。
- 资源检查 `main.py:20134-20145` 最多接收 3000 个 URL；虽然检查本身是轻量的，但请求体可能很大。

启动后台任务：

- `main.py:485-536` 的维护任务在启动 2.5 秒后开始，包含资产迁移、文件扩展名迁移、本地上传索引和视频片段对账。
- `main.py:538-557` 的任务恢复在 4 秒后开始，读取持久化任务并恢复状态。
- 两者都通过 `asyncio.to_thread` 执行，但仍会争用默认线程池和 SQLite；“不阻塞 `/api/health`”不等于“不影响用户点击后的请求”。

## 根因分级

### P0：媒体预览服务无并发控制和 in-flight 去重

**表现**：首次进入画布时大量缩略图长时间空白或陆续出现，CPU/磁盘占用高，视频预览尤其慢。  
**原因**：每张媒体独立触发 PIL/ffmpeg；相同资源并发请求会重复生成；没有优先级和队列。  
**影响**：直接对应“进入画布后所有资源很久才能加载”。

### P0：画布编辑器不是增量进入，而是 iframe 内整页冷启动

**表现**：点击画布卡片后长时间停留在旧页面或空白，再进入编辑器。  
**原因**：`window.location.href` 替换列表页文档，必须重新加载和编译 1 MB 级脚本；现有预热没有预热实际编辑器。  
**影响**：直接对应“点击画布工程时停滞很久”。

### P1：三路 iframe 预热制造瞬时主线程/内存峰值

**表现**：应用启动后较早点击画布比等待预热结束更慢；设备性能较弱时更明显。  
**原因**：并行加载多个重量级 iframe，且画布编辑器不在预热目标内。  
**影响**：放大 P0 的进入延迟，但不是媒体逐张生成的根因。

### P1：全量 DOM、几何、图标和 minimap 工作叠加

**表现**：节点越多、连接越多，首帧越慢；打开后浏览器主线程长任务明显。  
**原因**：render 全量构造节点/连接；特殊节点禁用部分 LOD；几何测量和 minimap 仍遍历全集。  
**影响**：中大型画布的 CPU 瓶颈。

### P1：异步 touch、资源检查和后台恢复缺少进入阶段隔离

**表现**：首帧已经显示但资源加载继续变慢，或启动后数秒内操作卡顿。  
**原因**：完整画布 touch 写入、资源检查、任务恢复和媒体预览同时发生。  
**影响**：增加尾延迟和抖动。

### P2：缓存策略和可观测性不足

**表现**：重复进入同一画布仍难以判断是网络、预览生成还是渲染慢；缓存命中收益不稳定。  
**原因**：媒体 URL 缺少内容版本；Service Worker 元数据每次读写；性能数据只在手动 `?canvasPerf=1` 时保存在内存。  
**影响**：无法快速回归和量化用户真实 p95。

## 建议的整改顺序

### 第一阶段：先止血（不改变画布数据模型）

1. 给 `/api/media-preview` 增加进程内 keyed in-flight cache（键为真实文件路径 + mtime + size + width），同一键只允许一个生成任务，其余请求等待同一 Future。
2. 增加媒体预览信号量，图片与视频分别限流；视频抽帧默认低并发，避免 ffmpeg 子进程洪峰。
3. 预览生成失败时返回可识别的占位结果并记录耗时，避免前端反复触发相同失败请求。
4. 前端首屏只加载当前视口节点的预览；滚动/平移进入视口后再加载。智能画布所有缩略图统一补齐 `loading="lazy" decoding="async"`。
5. 暂时把 iframe 预热并发从 3 降为 1，或在用户进入 canvas-list 后暂停其他页面预热；预热完成前点击画布应优先让出资源。

### 第二阶段：消除进入冷启动

1. 不在画布列表 iframe 内用 `window.location.href` 打开编辑器；改为在同一个画布宿主中维护 list/editor 两个视图，或预热一个真正的 `canvas.html` 文档并通过消息传入 canvas id。
2. 将 canvas.js 拆分为首屏核心、特殊节点、生成 provider、设置面板等 chunk；首屏只加载节点渲染和交互必需代码，其余在 idle 阶段加载。
3. 保留当前的“先 render、后台 touch/资源检查”原则，但把真正编辑器文档纳入预热验收。

### 第三阶段：降低大画布 render 成本

1. 以节点索引和视口 bounds 做首屏虚拟化，只创建可视区及安全边界内的节点 DOM。
2. 连接、minimap、图标刷新按 dirty 集合更新；避免首次 render 后再次全量 refresh。
3. 将原图尺寸测量改为按选中节点或用户打开编辑器时执行，禁止首屏对所有图片创建 `new Image()`。
4. 对历史日志、输出数组和节点媒体做服务端/客户端分页或上限裁剪，并在保存前剔除不可持久化的大型 data URL。

### 第四阶段：建立可观测性和回归门槛

记录以下阶段耗时并上报本地诊断日志：

- `canvas_navigation_start → canvas_html_loaded`
- `canvas_html_loaded → api_canvas_response`
- `api_canvas_response → first_render_end`
- `first_render_end → first_preview_paint`
- `/api/media-preview` 排队、生成、命中、失败耗时
- 首屏媒体数量、可视媒体数量、节点数、连接数、画布 JSON 字节数
- 长任务数量和最大持续时间

建议验收门槛：

- 轻量画布（≤50 节点、≤20 媒体）：首次进入到可交互 ≤1.5 秒。
- 中型画布（≤200 节点、≤100 媒体）：首次进入到可交互 ≤3 秒；首屏可视媒体先于非视口媒体显示。
- 同一画布第二次进入：不重新生成已存在的预览，媒体命中率 ≥95%。
- 100 个媒体并发请求时，预览生成队列不会超过设定并发，服务端无重复生成。
- 启动后台维护/任务恢复期间进入画布，p95 不得超过空闲状态的 1.25 倍。

这些测试证明现有契约（先 render、后台执行 touch/资源检查、部分交互增量更新）未被破坏，但没有证明真实媒体并发和 iframe 预热竞争已经解决。当前没有浏览器 HAR、Performance trace 或用户画布样本，因此无法给出真实 p95 数值；报告中的优先级依据代码路径和资源规模判断，实施第一阶段后应补充实测。

## 已知限制

- 仓库内示例数据库画布很小，不能用它推断真实用户画布规模。
- 本报告没有修改运行代码；因此不存在“问题已修复”的结论。
- 若用户实际使用的是独立 `smart-canvas.html` 路由而不是统一 `canvas.html`，智能画布的非 lazy 缩略图和全量 render 影响会更突出。
