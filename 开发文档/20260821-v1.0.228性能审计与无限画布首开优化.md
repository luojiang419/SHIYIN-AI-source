# v1.0.228 性能审计与无限画布首次进入优化

审计日期：2026-08-21
审计基线：`56a8e7d`（v1.0.228）
本轮实现提交：`c67a39c`、`5cbbba6`

## 一、结论

用户反馈的“软件重启后，首次进入任意无限画布项目等待很久”由多段启动工作叠加造成，核心不是画布详情接口本身，而是画布首屏被非关键数据串行阻塞：

1. 普通画布先等待运行时配置，再等待全部 RunningHub 工作流与 H3 状态，然后才打开项目；项目打开后还要等待打开记录写回和本地资源检查，最后才渲染。
2. 智能画布依次等待远程快捷键、提示词库、运行时配置、Kling/H3/RunningHub 能力、素材库和本地素材扫描，最后才请求项目。
3. 后端导入存储模块时同步递归扫描缓存和临时目录；文件很多时，健康检查和所有页面请求都会被整体推迟。

本轮已将项目详情和首屏渲染提升到最高优先级，并将全量缓存维护移出后端健康关键路径。代码层面已消除上述串行依赖，但受安装态登录会话和本轮浏览器控制不可用限制，未伪造毫秒级 A/B 数据；应使用新安装包重启实测最终体感。

## 二、本轮完成

### 2.1 普通无限画布

- 基础配置请求与画布详情请求并行启动。
- 画布数据返回后立即建立节点、连线、视口并渲染。
- 打开记录写回、本地资源存在性检查不再阻塞首屏。
- RunningHub 工作流和 H3 状态在空闲阶段补齐，完成后刷新控件。
- 资源检查绑定发起时的画布 ID，旧请求不能污染后来打开的项目。

### 2.2 智能无限画布

- 本地快捷键立即生效，远程快捷键随后同步。
- 项目详情与基础配置并行加载，项目函数自身完成首屏渲染。
- 提示词库、素材库、本地素材、Kling/H3/RunningHub 能力移入空闲任务。
- 非关键数据完成后自动刷新对应面板，不删除原有面板打开时的即时刷新。

### 2.3 后端冷启动

- `storage_bootstrap` 不再导入期执行 `MaintenanceManager.run_once()`。
- 首次缓存、临时文件和日志维护并入健康检查后的延迟维护队列。
- 每小时维护、10 GiB 默认缓存上限、20 GiB 硬上限和清理语义保持不变。
- `/api/runtime/info` 返回实时 `pending/running/complete/error` 维护报告，不再返回启动时静态快照。

## 四、仍需优化

### P1：CLI 超时后缺少进程树回收

`run_codex_cli()` 和 `run_jimeng_cli()` 在 `asyncio.wait_for(proc.communicate())` 超时后直接抛出 504，没有 `terminate -> wait -> kill -> wait`，Codex 临时输出也不在 `finally` 清理。CLI 卡住时可能遗留进程、孙进程和临时文件。

建议建立统一异步子进程执行器，Windows 使用 Job Object 或可靠的进程树终止，并覆盖超时、请求取消和后端退出。

### P1：部分上传仍先整文件读入内存

`/api/ai/upload` 仍使用 `await file.read()`，读取完成后才判断 50 MiB；多个文件或并发请求会叠加内存峰值。桥接包等新路径已使用 1 MiB 分块，说明项目已有可复用模式。

建议统一 `.part` 临时文件、读取过程硬上限、请求总量/文件数/并发限制和 `finally` 清理。

### P2：画布前端单文件过大且仍有全量重绘

- `static/js/canvas.js` 约 0.90 MiB。
- `static/js/smart-canvas.js` 约 0.96 MiB。
- 两个页面仍有大量操作调用全量 `render()`；大节点场景会重建 DOM、连线和小地图。

建议先按存储、生成、媒体编辑、特殊节点、渲染内核拆模块；再引入节点级 patch、连线/小地图脏标记和 300 节点以上视口裁剪。拆分必须保持现有全局兼容层，避免一次性重写。

### P2：延迟维护仍会在每次启动全量执行

历史扩展名修复、索引补偿和视频资产协调已不阻塞健康，但仍在每次启动运行。大量素材下会与启动后的用户操作争用磁盘。

建议为幂等历史修复增加迁移版本标记；新导入文件在入口即时校验，另保留管理员手动重建索引。

### P2：部分远程响应仍整块进入内存

代码中仍存在多处 `response.content`，其中一些用于图片等有界小对象，一些缺少统一字节上限。应按端点逐一分类：小 JSON/图片可保留，大视频、压缩包和未知远程文件必须流式处理。

### P3：框架与维护性债务

- `main.py` 约 0.94 MiB，路由、任务、存储和外部平台耦合，变更回归面大。
- FastAPI `on_event` 在全量测试中持续产生弃用警告，应迁移到 lifespan。
- Pydantic V2 下仍有 `.dict()` 弃用警告，应逐步改为 `model_dump()`。

## 六、后续验收基线

1. 冷启动：完成一次迁移后的健康检查 p95 小于 2 秒。
2. 首开：项目详情返回后立即出现可操作画布，不等待素材、提示词或外部能力探测。
3. 大画布：500 节点、1000 连线下拖动和缩放 p95 帧耗时小于 33 ms。
4. 子进程：任何超时、取消或退出后 2 秒内无 CLI 孤立进程，临时文件为 0。
5. 上传：超限文件在读取到阈值时立即中止，失败后无 `.part` 残留。
6. 存储：可再生成开发缓存和历史构建产物总量低于 20 GiB；不自动删除用户媒体、导出和差异备份。
