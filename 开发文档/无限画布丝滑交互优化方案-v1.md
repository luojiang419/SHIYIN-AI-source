# 无限画布丝滑交互优化方案 v1

日期：2026-08-22
适用范围：经典无限画布 `static/js/canvas.js`、智能无限画布 `static/js/smart-canvas.js`

## 1. 目标与硬指标

目标不是“平均更快”，而是让直接操作的反馈稳定在一帧内：

| 指标 | 目标 |
|---|---:|
| 端口连线、节点移动、画布平移/缩放 | p95 帧耗时 ≤ 16.7 ms，p99 ≤ 33 ms |
| 输出作品拖动中的 dragover 处理 | 单次处理 ≤ 1 ms，不触发重渲染、网络和图片解码 |
| 放下输出后首个节点外框出现 | ≤ 100 ms（不含上传/网络） |
| 端口命中反馈 | ≤ 16.7 ms，不能因大画布节点数线性放大 |
| 文本/下拉输入延迟 | p95 ≤ 50 ms |
| 500 节点 / 1000 连线 | 拖动、连线、缩放均不出现长任务（>50 ms） |

“无任何卡顿”需要以这些预算验收；浏览器图片解码、系统拖放和 GPU 调度仍需单独标注，不把不可控因素伪装成业务性能。

## 2. 已确认的卡顿根因

### 2.1 经典画布端口连线是确定性主因（P0）

`canvas.js:18063-18074` 的 `startLink()` 在每个 `mousemove` 直接调用 `renderLinks()`。该函数会清空并重建全部 SVG、全部连线删除按钮和命中路径（`18623-18651`），并重新读取所有端口 `getBoundingClientRect()`。因此连线拖动复杂度为每个事件 O(连线数 + 节点数)，且包含 DOM 读写交错；这是用户“从端口拖出线卡顿”的直接原因。

现有 `scheduleLinksRender()`（`1599-1607`）只被节点移动/缩放使用，未接入 `startLink()`。

### 2.2 智能画布端口拖拽每个 mousemove 做命中与全量 class 扫描（P0）

`smart-canvas.js:18103-18127` 每个 `mousemove` 执行 `elementFromPoint`、节点 `getBoundingClientRect`、`updatePortDragVisual()`；后者（`9290-9313`）每次查询并清除所有 `.node-port.is-active` 和 `.image-node.port-hover`。节点越多，命中和样式更新越昂贵。

### 2.3 输出作品拖入画布的 dragover 走了昂贵探测（P0）

`canvas.js:19028-19041` 先调用 `hasImageDropData()`，再判断 `hasOutputMediaDrag()`。前者会检查文件项、类型、文本候选和 payload；输出节点拖动本可由 MIME 类型 O(1) 判定，却在每个 dragover 事件重复做多分支探测。该路径还频繁切换 overlay class。

### 2.4 放下输出节点必然全量 render（P1）

`createMediaCardFromOutput()`（`15631-15640`）追加一个 image 节点后直接 `render()`；经典 `render()`（`7137-7181`）会遍历/重建所有节点、恢复媒体状态、刷新图标、图片兜底、小地图和连线。连线创建分支（`18075-18115`）也在成功连接后直接 `render()`。节点数增大时，用户会感觉“松手后卡住”。

### 2.5 输出拖拽预览可能触发额外布局/解码（P1）

`setOutputDragPreview()`（`15499-15514`）克隆原图元素并挂到 `body` 后调用 `setDragImage()`。对大缩略图/视频或高 DPI 场景，这会增加拖动开始时的布局和资源处理；应改为缓存的小型静态 ghost。

### 2.6 全量 render 和同步序列化是规模放大项（P1）

经典 `render()` 内仍有 `nodes.find()`（`7148-7150`、拖拽组收集 `17984-17989`）；`saveCanvas()`（`1828-1848`）在主线程执行完整节点序列化和 `JSON.stringify`。智能画布 `render()`（`8706` 起）也会重新拼接所有节点 HTML 和连接 SVG。小画布不明显，500+ 节点时会与交互帧争用主线程。

## 3. 总体架构：交互层、场景层、持久化层解耦

建立 `CanvasInteractionRuntime`（经典/智能共用协议）：

1. `pointerdown` 进入状态机并使用 `setPointerCapture()`；不再通过多个 `window.onmousemove` 互相覆盖。
2. 高频事件只更新内存坐标和少量 `style.transform`，通过一个统一 rAF 提交视觉更新。
3. 视觉更新拆成三条脏标记：`edgeDirty`、`selectionDirty`、`minimapDirty`；互不触发全量 render。
4. `render()` 降级为初始化、结构变化和显式恢复使用；属性变化、移动、连接、输出追加全部走 patch。
5. 保存走单飞队列：交互期间只记录 dirty revision，空闲 300–500 ms 后序列化；连续拖动不能启动多个 JSON 序列化。

## 4. 分模块实施步骤

### 模块 A：性能基线与观测（先做）

- 增加 500/1000/2000 节点与连线的可重复 fixture。
- 通过 `PerformanceObserver` 记录 long task、Event Timing、rAF 帧耗时；记录 `pointerdown→paint`、`drop→node-visible`。
- 在开发模式显示 FPS、当前节点/连线数、最近一帧耗时、最近一次全量 render 原因。
- 先不改业务逻辑，形成基线报告，作为每个后续模块的回归门槛。

### 模块 B：统一拖拽调度器（P0）

- 经典 `startLink()` 改为 `tempLink` 坐标即时更新 + `scheduleLinksRender()`，每帧最多一次。
- 智能 `portDragState` 命中计算改为 rAF；缓存节点 DOM 矩形和端口矩形，只有命中节点变化时更新 class，并保存上一个 active 元素，禁止全量 `querySelectorAll` 清理。
- 节点拖动、缩放、框选、画布平移、端口连接使用同一 pointer capture 生命周期，结束时统一清理。

### 模块 C：增量连线渲染器（P0）

- 首次 render 建立 `connectionId → {path, hit, control}` 映射；后续只更新受影响连线的 `d`、位置和 class。
- 端点几何缓存按 `nodeId/portRole/viewportRevision` 失效；拖动节点只让相邻连线进入 dirty set。
- 删除/新增连线只增删对应 SVG 元素，不清空 `linksEl`。
- 端口拖拽临时线使用单独 path，直接改 `d`，不重建全部连线。
- 大于 120 条连线继续关闭几何 hover 兜底；优先依赖透明 hit path。

### 模块 D：输出拖放快路径（P0）

- `dragover` 首先判断 `hasOutputMediaDrag()`，命中后直接 `preventDefault + dropEffect`；普通文件探测放到后面。
- overlay 状态只在进入/离开目标变化时切换，不能每个 dragover 重复 class 写入。
- 预览 ghost 使用固定 96×96 的 CSS/SVG 缩略图缓存，不克隆原媒体元素。
- `drop` 只创建节点模型并调用 `patchNodeCreate()`；网络、图片 natural size 测量、缩略图解码移出当前交互帧。

### 模块 E：节点级 patch 与结构事务（P1）

- 新建 image/output/generator 节点：`nodes.push`、索引更新、创建一个 DOM 节点、必要连线增量插入；不触发全量 `render()`。
- 连接成功：只 patch 两端输入预览、增量更新连接、异步 `syncGeneratorInputs`；若输入预览需重排，限制在目标生成器节点。
- `refreshNodes(ids)` 继续保留，扩展为 `patchNode(nodeId, reason)`，并让输出列表追加/删除只更新对应 grid 子树。
- 结构性动作（批量导入、分组、撤销恢复）才允许全量 render，并在开发面板记录原因。

### 模块 F：大画布 LOD 与视口裁剪（P1）

- 节点数 > 200 开启可视区 + 1.5 屏缓冲裁剪；只保留可见节点 DOM，连接层使用几何缓存绘制可见端点。
- 节点数 > 500 时关闭非必要阴影、复杂 hover、媒体自动播放和小地图全量重建；小地图改 Canvas 绘制。
- 将 `nodes.find` 全部替换为 `nodeIndex`，拖拽组收集使用索引。

### 模块 G：媒体与持久化隔离（P1）

- 输出缩略图固定尺寸、`content-visibility:auto`、懒加载；拖拽期间禁止 decode/natural size 测量。
- 保存序列化放入 Worker（或至少在空闲回调执行），采用 revision 检查避免旧快照覆盖新编辑。
- `scheduleSave` 增加最大等待上限，保证停止操作后最终保存，但不阻塞 pointer 事件。

## 5. 实施顺序与回滚

顺序：A → B → C → D → E → F → G。每个模块独立开关：`canvasPerfFlags.interactionRaf`、`incrementalLinks`、`dropFastPath`、`virtualizeNodes`。任一模块回归时只关闭对应开关，不回滚其他模块。

每完成一个模块：运行经典/智能画布专项测试、500 节点基准、浏览器长任务采样；生成进度快照。完成 E/G 等大模块后再做源码备份。

## 6. 验收场景

1. 端口输出→输入：连续拖动 2 秒，p95 帧 ≤ 16.7 ms，线条无跳帧，松手后连接 ≤ 100 ms 可见。
2. 输出缩略图→画布：拖动 2 秒，dragover handler p95 ≤ 1 ms；松手后节点外框 ≤ 100 ms 可见，图片随后加载。
3. 输出节点→空白画布：自动创建输出节点的场景同上，不能在松手时全量重建。
4. 500 节点/1000 连线：移动、连线、缩放各 30 秒；long task >50 ms 次数为 0 或仅限结构变化。
5. 输入文本、撤销、远程同步、媒体播放、分组、删除、刷新恢复：功能结果与当前版本一致。

## 7. 不应采用的“伪优化”

- 不通过降低画布分辨率、删除连线、关闭用户可见反馈来换 FPS。
- 不在每个事件里 `setTimeout` 堆积任务；必须使用可取消的 rAF/单飞队列。
- 不把所有 DOM 放入 Shadow DOM 或一次性重写框架；当前全局模块兼容成本过高。
- 不在没有基准的情况下声称“零卡顿”；每次改动必须给出同一 fixture 的 p50/p95/p99。
