# 电商工作流节点故障分析与修复方案

## 1. 结论摘要

当前问题不是单一的上传接口故障，而是电商节点协议没有完整接入经典画布的“输入端口、分组素材透传、上传容错”三条公共链路，最终表现为：

1. 电商模特、电商产品、电商场景三个节点被实现为纯本地上传源节点，`inputPorts()` 明确返回空数组，且 `canConnect()` 明确禁止它们作为上游被外部输入驱动。
2. 节点组只提取普通 `image` 子节点，不提取组内电商节点的 `ecomItems`；将电商节点放入组后，组虽然有输出端口，但不能向 A+ 图合成提供电商参考图。
3. 电商上传只按浏览器 MIME 类型筛选图片。部分桌面 WebView、系统文件选择器或拖拽场景会返回空 MIME，导致图片在请求前被静默过滤，用户看到的就是“无法上传”。上传失败时还丢失了后端具体错误。
4. 现有测试主要是源码字符串契约，没有验证最终 DOM 中的端口数量、分组后素材是否可用、MIME 为空时的上传行为，因此测试全绿不能证明此功能可用。

电商场景生成和 A+ 图合成的后端接口本身存在，电商工作流创建器也写入了正确的四条连接；因此不建议先重写后端生成任务，应该先修复前端节点协议和素材传递，再补运行时回归。

## 3. 根因论述

### 3.1 P0：源节点输入协议缺失，导致外部素材无法进入电商源节点

证据位置：`static/js/canvas-ecommerce-nodes.js:99-108`。

当前实现只有 A+ 图合成节点声明四个角色端口：模特、商品、场景、动作；电商视频声明一个通用输入端口。模特、产品、场景直接落入 `return []`。

画布渲染层在 `static/js/canvas.js:9648-9659` 根据 `inputPorts()` 决定是否创建 `.port.in`。因此三个源节点不会产生输入端口，这是代码确定的行为，不是 CSS 偶发丢失。

连接校验进一步在 `static/js/canvas.js:19261-19275` 固化了这一语义：

- A+ 图合成只接受指定 `inputRole` 的上游连接。
- `ecom-model/product/scene` 作为上游时允许被 A+ 图合成使用。
- 但后续 `if(['ecom-model','ecom-product','ecom-scene'].includes(from.type)) return false;` 禁止这些节点继续接受任何上游输入。

因此当前节点实际上是“手动上传型素材源”，不是可被画布其他节点驱动的电商输入节点。若产品需求是“每个电商节点都可以接入图片节点、组节点或普通生成节点”，当前协议与需求不一致。

### 3.2 P0：节点组没有电商素材适配器，组内电商节点会丢失输入

证据位置：`static/js/canvas.js:13685-13710`。

`mediaRefsFromNode()` 对 `group` 的处理只遍历：

```text
node.items -> type === 'image' && url
```

它不会递归或分派到 `mediaRefsFromNode(child)`，也不会读取电商节点的 `ecomItems`。所以把 `ecom-model`、`ecom-product` 或 `ecom-scene` 放入普通组后：

- 组本身仍可渲染一个输出端口，因为普通组在 `canOutput` 列表中。
- 组的输出参考图列表为空，A+ 图合成收到的 `inputs` 为空。
- `runEcommerceComposeNode()` 最终命中“请至少连接一个电商模特、商品、场景或参考图片”。

分组逻辑在 `static/js/canvas.js:17374-17390` 可以把任意非组节点放入 `items`，但分组后的素材抽取逻辑没有同步扩展，这是数据结构允许、消费逻辑不支持的契约断裂。

另外，普通组在当前设计中是“素材聚合输出组”，不是“带输入端口的容器节点”。因此需要把“组内子节点没有输入端口”和“组本身没有输入端口”分开处理：前者是电商节点能力缺失，后者是组模型定义缺少明确产品语义。

### 3.3 P1：电商上传过滤条件过窄，可能在请求前静默丢弃图片

证据位置：`static/js/canvas-ecommerce-nodes.js:170-178`。

当前代码只接受：

```text
String(file.type || '').startsWith('image/')
```

画布公共上传链路已经在 `static/js/canvas.js` 中同时检查 MIME 和文件扩展名，而电商节点没有复用这套判定。对于 `file.type === ''` 但文件名为 `product.png` 的场景，`accepted` 为空，函数直接返回空数组，不会请求 `/api/ai/upload`，用户也看不到明确错误。

即使请求发出，非 2xx 响应也统一变成“图片上传失败”，后端返回的 400、401、413 或图像解码错误不会展示给用户。后端接口 `main.py:11385-11442` 确实存在，并且会保存和返回 `url/name/kind`；现有证据不足以认定后端路由缺失，上传链路的首要问题在前端过滤和错误可见性。

### 3.4 P1：测试验证了实现痕迹，没有验证用户可操作结果

`tests/test_canvas_ecommerce_workflow.py` 主要通过 `assert "..." in source` 验证菜单、函数名、连接字符串和请求字段。当前没有覆盖：

- 五类节点实际渲染后的 `.port.in` 数量与 `data-input-role`。
- `canConnect()` 与端口定义是否一致。
- 组内电商节点的 `ecomItems` 是否能透传到合成节点。
- 图片 MIME 为空时是否仍能上传。
- 上传接口返回 400/401/413 时是否保留后端错误。
- 真实按钮事件是否绑定在当前节点 DOM 上。

这解释了为什么测试全绿而用户仍然感知为“所有节点无法工作”。

### 3.5 非首要根因：后端电商任务链路目前不是明显断点

证据位置：`static/js/canvas.js:9062-9132`、`main.py:15442-15485`。

前端已有场景任务和 A+ 图任务创建、轮询、结果回写逻辑；后端已有能力查询、任务创建、状态查询和执行任务。当前问题应先避免扩散为后端重构。实际生成仍依赖已配置的图像/视频模型和账号权限，这属于运行前置条件，需要在验收中单独区分。

## 4. 修复目标

修复后应满足以下产品契约：

1. 电商源节点可以手动上传，也可以从画布其他媒体节点接收输入。
2. 每个有输入能力的节点都有稳定、可识别的输入角色；端口 DOM、连接数据和执行参数使用同一角色标识。
3. 普通组可以聚合组内普通图片、生成结果和电商节点参考图，并将其作为下游输入；组的输入端口是否开放需要明确产品语义后实施。
4. 上传判定兼容 MIME 为空的本地文件，并向用户展示后端具体错误。
5. 旧画布数据保持可加载；新增端口只影响后续连接，不破坏历史 `ecomItems` 和已有连接。

## 5. 推荐修复方案

### 5.1 模块一：建立统一的电商端口能力表

在 `static/js/canvas-ecommerce-nodes.js` 内将 `inputPorts(type)` 扩展为完整协议，建议角色如下：

| 节点 | 建议输入角色 | 说明 |
|---|---|---|
| `ecom-model` | `model-reference` | 接收人物主体/身份参考，允许多条连接并按顺序合并 |
| `ecom-product` | `product-reference` | 第一条为主商品，其余作为细节证据 |
| `ecom-scene` | `scene-reference` | 接收场景图；与手动生成场景结果按明确优先级合并 |
| `ecom-compose` | 保留 `ecom-model/ecom-product/ecom-scene/ecom-pose` | 兼容现有工作流连接 |
| `ecom-video` | 将空角色改成 `video-input` | 避免空字符串端口与普通输入语义混用 |

同时提供 `inputPort(type, role)` 或等价能力查询函数，供 `renderNode()` 与 `canConnect()` 共用，避免继续在 `canvas.js` 中维护第二份硬编码白名单。

实施要点：

- 端口角色名必须兼容历史连接；旧的 `ecom-model` 等 A+ 图角色不能改名。
- 对允许多图的节点，连接数量限制、排序和手动上传合并规则要集中定义。
- 渲染时即使只有一个角色端口，也要保留 `data-input-role`，不要退化成无角色的普通 `.port.in`。
- `ecom-video` 的通用端口也应写入明确角色，读取历史空角色连接时做迁移兼容。

### 5.2 模块二：统一参考图组装逻辑

新增一个不直接修改节点状态的读取函数，例如 `ecommerceInputRefs(node)`，按以下顺序得到输入：

1. 节点手动上传的 `ecomItems`。
2. 按端口角色读取上游节点的 `mediaRefsFromNode()`。
3. 对普通图片、输出节点、生成节点、组节点统一转换成电商参考图结构。
4. 按节点类型执行角色映射、数量限制和去重。

`mediaRefsFromNode()` 对 `group` 应改为递归分派子节点：

- 普通 `image`：保留现有行为。
- 电商节点：调用电商模块的 `mediaRefs()`。
- `output`、普通生成节点和特殊节点：复用现有分支。
- 嵌套组：设置递归深度上限并防止循环引用。

这样组内电商节点不会因为组适配器只认识 `image` 而丢失。

### 5.3 模块三：明确“节点组输入端口”的产品语义

推荐第一阶段把普通组定义为“聚合输出节点”：组本身只提供输出端口，组内电商节点各自提供输入端口。这样可以修复实际素材丢失问题，且不会改变现有组的连线方向。

如果产品真实意图是“把整个电商工作流作为可复用节点组，外部只连接组的输入端口”，则需要第二阶段增加组端口模型：

- 为组保存 `exposedInputs`，包含角色、子节点 ID、子节点端口角色。
- 组渲染暴露角色化输入端口。
- 外部连接写入组，运行时将组输入映射到内部节点。
- 删除/移动组成员时同步维护暴露端口。

这不是简单把 `group` 加入 `canInput` 列表；直接加一个普通输入端口会产生连接无法映射到哪个子节点、执行时也无人消费的问题。建议在确认产品语义前，不实施这个高风险扩展。

### 5.4 模块四：修复上传链路并复用公共能力

建议抽取共享的 `isSupportedImageFile(file)` 和 `uploadImageFiles(files, options)`，供普通画布与电商节点共同使用；至少应做到：

- MIME 为空时回退到文件名扩展名判断。
- 支持前端实际允许的图片扩展名集合。
- 保留后端响应中的 `detail`，将 400/401/413/500 转为可读错误。
- 对空文件、超限文件、无有效图片的情况分别提示。
- 上传成功后按后端返回顺序写入节点，限制数量并避免重复。
- 请求支持取消或节点删除后的结果丢弃，避免异步回调把图片写回已删除节点。

后端可在第二阶段补充结构化错误码和最大上传大小，当前不需要重写存储路径；`main.py:11385-11442` 的保存、方向校正和内部媒体注册流程应继续复用。

### 5.5 模块五：缓存版本与旧数据兼容

修改 `static/js/canvas-ecommerce-nodes.js` 或 `static/js/canvas.js` 后，同步递增 `static/canvas.html` 中脚本 query 版本，避免桌面 WebView 继续使用旧脚本。

加载旧节点时：

- 缺少 `ecomItems` 仍初始化为空数组。
- 历史 `ecom-model/product/scene` 节点无需迁移 ID。
- 历史 A+ 图连接的 `inputRole` 原样保留。
- 历史电商视频空角色连接迁移到 `video-input` 时必须保留反向兼容读取。

## 6. 实施顺序

### 阶段一：协议和上传止血

- 补全五类节点的端口定义与 DOM 角色属性。
- 将 `canConnect()` 改为调用统一端口能力判断。
- 修复 MIME 为空的图片识别和错误信息展示。
- 加入端口渲染、连接校验、上传请求的单元/契约测试。

### 阶段二：分组和执行链路

- 统一 `ecommerceInputRefs()`。
- 让 `group` 递归提取电商参考图。
- 验证手动上传、普通图片节点、生成节点、组节点四类来源都能进入 A+ 图合成。
- 验证 A+ 图结果进入电商视频，并能回写输出。

### 阶段三：可选的组输入端口

- 先确认组是“聚合输出”还是“可复用子工作流容器”。
- 若选择容器语义，再设计 `exposedInputs`、内部映射和组级运行状态。
- 单独做旧画布迁移和删除成员回收测试。

## 7. 验收标准

### 7.1 端口和连线

- 单独创建五类电商节点，DOM 端口数量符合能力表。
- 模特、产品、场景输入端口可接普通图片、普通组和生成输出。
- A+ 图合成的四个端口角色不变，历史工作流连接仍可识别。
- 电商视频输入端口可接 A+ 图结果，空角色历史连接仍能运行。
- 非法媒体类型、循环连接和无效角色连接被拒绝并有明确提示。

### 7.2 上传

- MIME 正常的 PNG/JPEG/WebP 可以上传。
- MIME 为空但扩展名正确的本地图片可以上传。
- 多图节点分别验证 2 张、8 张上限。
- 超过 50MB、损坏图片、未登录请求都显示后端具体原因。
- 上传完成后刷新画布，节点图片仍可恢复，URL 能被下游执行读取。

### 7.3 节点组和运行

- 组内普通图片、电商模特、电商产品、电商场景均能向组外 A+ 图节点提供参考图。
- 组内电商节点的角色、数量和细节图关系不丢失。
- 场景生成、A+ 图合成、电商视频三段级联分别完成，失败时后续节点不会假成功。
- 重启服务和重新打开画布后，节点、连接、上传素材、任务状态均可恢复。

## 8. 风险与不应采用的修复

- 不要只在 CSS 中移动端口；当前三个源节点没有生成端口 DOM，CSS 无法修复。
- 不要只把 `group` 加入输入白名单；没有内部映射时，连接会显示成功但执行仍拿不到素材。
- 不要删除现有 `ecomItems` 改为完全依赖普通图片节点；这会破坏现有手动上传工作流和历史画布。
- 不要先重写电商后端任务；当前证据更支持前端端口/分组/上传契约断裂。
- 不要以源码字符串测试代替 DOM 和真实事件测试。

## 9. 待确认的产品决策

需要确认的不是“是否修复”，而是节点组的目标语义：

- **推荐选项 A：** 普通组继续作为素材聚合输出组；修复组内电商节点输入端口和电商素材递归透传。
- **选项 B：** 普通组升级为可复用的工作流容器；增加组级角色化输入端口、内部映射和组级执行状态，开发量和迁移风险明显更高。

在没有选择 B 之前，按 A 实施可以直接解决“组内电商节点无输入、组后合成拿不到图片”的用户故障，同时保持现有组模型稳定。

## 10. 本轮边界

本轮只完成分析和修复设计，没有修改业务源码、没有创建备份版本，也没有向 GitHub 推送。报告依据当前工作区源码、Git 历史、测试结果和本地服务启动结果编写；真实账号下的浏览器上传和生成任务仍需在修复后按验收矩阵执行。
