# 生成占位必须具备可恢复任务身份

## 问题

图片或视频任务已经生成成功、真实媒体也已回填到输出节点，但节点里仍残留一个持续转圈并累计时长的输出占位符。重新打开画布后，该占位仍可能继续存在。

## 原因

普通画布使用输出节点的 `_pending` 数组保存生成等待项。部分在线任务会先创建占位，再异步取得 `canvasTaskId`：

1. 创建 `_pending` 占位并显示 spinner。
2. 提交后端任务。
3. 取得 `canvasTaskId` 并写回占位。
4. 轮询完成后按任务 ID 找到占位，删除占位并回填媒体。

如果第 2～3 步之间发生保存、重载、同步或中断，就可能持久化一个既没有 `canvasTaskId`、也没有 `recoverTaskId` 的占位。它无法进入恢复轮询，也无法被后续完成回调按任务 ID命中，因而成为永久转圈的“孤儿占位”。

## 解决

- 在新建或打开画布的加载边界，删除没有 `canvasTaskId` 和 `recoverTaskId` 的不可恢复输出占位。
- 在运行中的输出定时刷新里，如果来源生成节点已经明确处于 `runStatus === 'done'` 且不再 `running`，清理该来源遗留的无任务 ID 占位。
- 保留带 `canvasTaskId` 的正常图片/视频任务，以及带 `recoverTaskId` 的失败查询项。
- 远端增量同步继续使用保守模式，不在同步瞬间清理无任务 ID 占位，避免误删刚提交但尚未取得任务 ID 的活跃任务。

## 后续规则

1. 需要跨刷新恢复的等待态必须持久化唯一任务身份；只有视觉状态、没有恢复键的 spinner 不应长期保存。
2. 完成回填必须同时处理媒体状态和等待状态，不能只向 `images` 或 `generatedOutputs` 追加结果。
3. 清理逻辑要区分“加载边界”和“运行中同步”：加载时可删除不可恢复状态，增量同步时必须保护提交窗口。
4. 可恢复失败项必须保留，不能为了消除 spinner 一律清空 `_pending`。
5. 回归测试至少覆盖：孤儿占位清理、正常任务保留、可查询失败项保留、防递归刷新。
